# 26 — Security Requirements (Conceptual)

AuthN: password hashing (argon2/bcrypt) + MFA optional (required for Admin/Owner); session expiry + refresh rotation; lockout after 5 fails. AuthZ: RBAC `resource.action` + warehouse scope enforced server-side on EVERY request (never trust client filter). SoD creator≠approver. Sensitive ops (approve/apply/ship/receive/dispose/user-role changes) require re-auth or step-up + explicit reason + audit. Input: validate SKU/qty/dates/files; allowlist uploads (jpg/png/pdf/xlsx/csv, ≤10MB), virus-scan hook. API: bearer short-lived, rate-limit reservation/lookup/login, idempotency keys, CORS allowlist, no stock write via GET. Secrets via vault/env, never in repo/logs. PII: minimal (contacts); audit masks sensitive fields. Backups encrypted; restores tested (see 28).

## Build decisions (Part 10, normative)

- **Step-up (re-auth):** a web-session call that needs a sensitive grant must come from a session signed in within the last **30 minutes**; otherwise `forbidden` with `details.reason = "step_up_required"` (audited as `access.denied`) and the user signs in again (password + TOTP when enrolled). Sensitive grants: every approve grant (`purchases.approve`, `*_approve`), `inventory.count_apply`, `inventory.adjust_apply`, `inventory.receive`, `inventory.transfer_ship`, `inventory.transfer_receive`, `purchases.return_ship`, `sales.return_receive`, `users.manage`, `roles.manage`. Checked inside `requirePermission` only when *every* grant the call accepts is sensitive (a call that also accepts a view grant is a read). API keys (service users) and system jobs are exempt: they are not interactive sessions. The "explicit reason" is the document's own reason (adjustment/damage/dispose reason code, reject comment, return reason); approve keeps its optional comment.
- **Rate limits** (fixed 60 s window, per client = API key, else session cookie, else IP): sign-in 10/min per IP; `POST /api/reservations` and `POST /api/pos-sales` 300/min; `POST /api/products/lookup` 600/min (scan bursts). Over the limit → 429 `rate_limited` with `Retry-After` (doc 24). Brute force on one account is also stopped by the 5-fail lockout.
- **CORS:** allowlist from `CORS_ORIGINS` (comma-separated origins), never a wildcard. A state-changing `/api` request whose `Origin` is neither the app's own host nor allowlisted is rejected `forbidden` (CSRF defence in depth on top of SameSite cookies).
- **Headers:** CSP (`default-src 'self'`, no framing, no plugins), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera only for the app itself, for scanning), HSTS in production, no `X-Powered-By`.
- **Secrets:** only in env / the host's secret store; `.env*` is git-ignored except `.env.example` (placeholders). Env is validated at boot (web + worker); production refuses a short or placeholder `BETTER_AUTH_SECRET`.
