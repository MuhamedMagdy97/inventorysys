# 26 — Security Requirements (Conceptual)

AuthN: password hashing (argon2/bcrypt) + MFA optional (required for Admin/Owner); session expiry + refresh rotation; lockout after 5 fails. AuthZ: RBAC `resource.action` + warehouse scope enforced server-side on EVERY request (never trust client filter). SoD creator≠approver. Sensitive ops (approve/user-role changes) require re-auth or step-up; apply/ship/receive/dispose require an explicit reason + audit (owner decision 2026-10-09: no step-up for floor operations). Input: validate SKU/qty/dates/files; allowlist uploads (jpg/png/pdf/xlsx/csv, ≤10MB), virus-scan hook. API: bearer short-lived, rate-limit reservation/lookup/login, idempotency keys, CORS allowlist, no stock write via GET. Secrets via vault/env, never in repo/logs. PII: minimal (contacts); audit masks sensitive fields. Backups encrypted; restores tested (see 28).

## Build decisions (Part 10, normative)

- **Step-up (re-auth):** a web-session call that needs a sensitive grant must come from a session signed in within the last **30 minutes**; otherwise `forbidden` with `details.reason = "step_up_required"` (audited as `access.denied`) and the user signs in again (password + TOTP when enrolled). Sensitive grants: every approve grant (`purchases.approve`, `*_approve`), `users.manage`, `roles.manage`. Floor operations (receive, ship, transfer receive, return ship/receive, count/adjust apply) are deliberately not step-up: warehouse staff post them all day, and they stay audited and permission-checked (owner decision 2026-10-09). Checked inside `requirePermission` only when *every* grant the call accepts is sensitive (a call that also accepts a view grant is a read). API keys (service users) and system jobs are exempt: they are not interactive sessions. The "explicit reason" is the document's own reason (adjustment/damage/dispose reason code, reject comment, return reason); approve keeps its optional comment.
- **Rate limits** (fixed 60 s window, per client = API key, else session cookie, else IP): sign-in 10/min per IP; `POST /api/reservations` and `POST /api/pos-sales` 300/min; `POST /api/products/lookup` 600/min (scan bursts). Over the limit → 429 `rate_limited` with `Retry-After` (doc 24). Brute force on one account is also stopped by the 5-fail lockout. Counters live in Postgres (`rate_limit_hit`, one row per key; the window starts at the key's first hit; one `INSERT … ON CONFLICT DO UPDATE … RETURNING` per limited request, times from the DB clock), so the limit holds across web replicas; GETs and unlimited routes never touch it; the worker purges ended windows every 5 min. **Fail-open:** if the counter write errors, the request passes and the error is logged: a DB blip must not lock users out of sign-in/POS, the request itself needs the DB anyway, and per-account brute force stays covered by the lockout. (The proxy runs on the Node.js runtime in Next 16, so it uses the shared Prisma pool.)
- **CORS:** allowlist from `CORS_ORIGINS` (comma-separated origins), never a wildcard. A state-changing `/api` request whose `Origin` is neither the app's own host nor allowlisted is rejected `forbidden` (CSRF defence in depth on top of SameSite cookies).
- **Headers:** CSP (`default-src 'self'`, no framing, no plugins), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera only for the app itself, for scanning), HSTS in production, no `X-Powered-By`.
- **Secrets:** only in env / the host's secret store; `.env*` is git-ignored except `.env.example` (placeholders). Env is validated at boot (web + worker); production refuses a short or placeholder `BETTER_AUTH_SECRET`.
- **Outbound webhooks (Part 11, doc 24):** HMAC-SHA256 signature over `timestamp.body` with a per-endpoint secret shown once; the secret is never logged, audited or returned after create/rotate. SSRF guard, checked at save time (scheme, `localhost`, literal addresses) and again at every attempt on the address actually connected to (the DNS lookup is validated inside the connection, so a rebinding hostname can't slip through): in production only `https` URLs, and loopback, private (RFC 1918), link-local, CGNAT, unique-local, multicast and unspecified addresses are refused; outside production `http` and local addresses are allowed (dev receivers, tests). Redirects are never followed; responses are not read beyond the status code.
