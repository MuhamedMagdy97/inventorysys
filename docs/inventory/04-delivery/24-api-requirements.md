# 24 — API Requirements (Conceptual, No Code)

Conventions (binding for later build): REST/JSON; auth bearer+refresh; every stock-mutating POST requires client `Idempotency-Key` header (server maps header→result AND stores derived per-leg keys per MV-02); every state-changing PATCH/POST requires current `version` (optimistic locking, INV-023); errors `{code, message, details, trace_id}` with codes: `insufficient_stock, reserved_conflict, batch_insufficient, invalid_transition, version_conflict, archived_conflict, discontinued_conflict, reservation_expired, forbidden, not_found, conflict, validation_error, duplicate, rate_limited` (`rate_limited` = HTTP 429 with a `Retry-After` header and `details.retryAfterSeconds`; added in Part 10 for the doc 26 rate limits). Pagination `?page&per_page&sort&filter`; scope filtering server-side by company + warehouses. All mutating responses include resulting balances + movement ids + audit id.

Groups:
- **Products:** CRUD + archive, variant mgmt, category/brand mgmt, bulk lookup by SKU/barcode (`POST /products/lookup` for scans — `:` can't appear in a route folder name; returns every match per code, never auto-picks). Perms per doc 02. Errors: `duplicate` (`details.field` = sku|barcode), `conflict` with `details.reason = "immutable_flag"`.
- **Inventory:** `GET /availability?v&wh` (ATP), `GET /balances`, `GET /movements` (ledger, filterable), reserve/release/fulfil endpoints (atomic, TTL, allow_partial). Business rules INV-001/002/004.
- **Warehouses:** CRUD + bins + assign users. Archive guards WH-02/03.
- **Purchasing/Receiving:** PO CRUD + submit/approve/reject/order/close/cancel; receipts post (multipart lines with batches/serials); returns lifecycle. Idempotent GRN numbering server-side.
- **Transfers:** request/submit/approve/ship/receive(+variance resolve). Ship/receive validate ATP + serials/batches.
- **Returns:** both flows + inspection decisions.
- **Counts:** open/snapshot/submit/variance/approve/apply/recount endpoints (snapshot semantics per INV-023).
- **Inspection:** quarantine list, inspect decisions (restock/damage/expire/dispose with evidence refs), excess-delivery approve/reject.
- **Opening/repair/disposal:** dedicated endpoints under `inventory.*` grants with dual-control (creator≠approver).
- **Reports:** run with filters → sync CSV/Excel (async for large, job id + download).
- **Users/Roles/Audit/Notifications/Settings/Imports:** standard CRUD + run + history. Imports: upload→preview→confirm two-phase.
- **Webhooks (V1.5):** stock.low, stock.out, reservation.expired, po.approved, transfer.received.

Rate limits on reservation/lookup (scan bursts); input validation (SKU format, qty>0, future expiry); file upload allowlist + size caps.

## Webhooks — build decisions (Part 11 T11.4, normative)

- **Endpoints** are per company: `url`, `events` (non-empty subset of the five types below), `status` (`active` | `disabled`), a description. Managed by the `webhooks.manage` grant (Super Admin + Administrator seed roles) on `/admin/webhooks`; every change is audited (`webhook.create/update/rotate/enable/disable`; the secret never appears in audit). Nothing is deleted: an endpoint is disabled.
- **Secret:** `whsec_` + 32 random bytes (base64url), generated by the server, shown **once** (on create and on rotate) and never returned again. Stored server-side because signing needs it.
- **Events** (`type` → `data`):
  - `stock.low` / `stock.out` — a posting (any `postMovements` call, reservations included) moves warehouse-level *available* (`SUM(on_hand) − SUM(qty_reserved)` over all batches of the variant in the warehouse) across a threshold: `stock.out` when it goes from > 0 to ≤ 0; `stock.low` when it goes from above the warehouse reorder point (`variant_warehouse_settings.reorder_point`, none = never low) to ≤ the reorder point while still > 0. Edge-triggered: staying low emits nothing; climbing back above and dropping again emits again. `data = {variantId, sku, warehouseId, warehouseCode, available, availableBefore, reorderPoint, sourceType, sourceId}`. The daily notification digest (doc 17) is unchanged.
  - `reservation.expired` — the expiry job released a reservation past its TTL. `data = {reservationId, variantId, warehouseId, salesOrderRefId, qtyReleased}`.
  - `po.approved` — `data = {purchaseOrderId, number, supplierId, warehouseId, total, currency, approvedBy}`.
  - `transfer.received` — every receive posting on a transfer (partial receives too). `data = {transferId, number, fromWarehouseId, toWarehouseId, status, lines: [{variantId, sku, received, damaged, missing}]}`.
- **Outbox:** the event row and one delivery row per subscribed active endpoint are written **in the business transaction** (rolled back with it). No subscribed endpoint → nothing is written.
- **Payload** (POST, `content-type: application/json`): `{"id", "type", "created_at" (ISO 8601 UTC), "company_id", "data"}`. `id` is the event id (UUIDv7) and is identical on every retry: receivers dedupe on it (delivery is at-least-once).
- **Headers:** `Webhook-Id: <event id>`, `Webhook-Timestamp: <unix seconds of this attempt>`, `Webhook-Signature: v1=<hex HMAC-SHA256(secret, "<timestamp>.<raw body>")>`. Receivers recompute over the raw body, compare in constant time, and reject timestamps more than 5 minutes off.
- **Delivery** (worker job `webhook-deliver`, every minute): 2xx within 10 s = delivered. Anything else (non-2xx, timeout, DNS/connection error, a redirect — redirects are not followed, SSRF guard refusal) = failed attempt. Retries after **1 min, 5 min, 30 min, 2 h, 6 h** (6 attempts in total), then the delivery is `failed`. A delivery is claimed with a 2-minute lease before the request, so two workers never send it concurrently and a crash mid-request retries it.
- **Auto-disable:** an endpoint's consecutive failed attempts are counted (reset by any success); at **15** the endpoint is `disabled` (audit `webhook.disable`, reason `too_many_failures`, notification to `webhooks.manage` holders) and its pending deliveries are marked `failed`. Re-enabling resets the counter; old failed deliveries are not resent.
- **Delivery log:** per (event, endpoint): status `pending | delivered | failed`, attempts, next attempt, last HTTP status, last error (≤ 500 chars), delivered at. Shown on the endpoint page (latest 50).
- **Scope:** endpoints and events are company-wide (an endpoint sees stock events of every warehouse), so `webhooks.manage` is not warehouse-scoped; every query filters by `company_id`. Endpoints are managed in the UI only (no REST route in V1.5).
